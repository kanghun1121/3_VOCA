# Mobile App Architecture

실제 앱을 만들기 위한 설계 결정을 내리고 구현 계획과 코드 뼈대를 산출하는 스킬이다.

이 스킬의 전제는 두 가지다.

> **결정은 취향이 아니라 숫자 기준으로 내린다.**
> **도입 판단만큼 미도입 판단이 중요하다.**

대부분의 모바일 설계 실패는 두 방향 중 하나다. 화면 세 개짜리 앱에 계층을 다섯 개 쌓거나, 화면 여든 개짜리 앱을 ViewModel 하나로 버티거나. 그래서 이 스킬은 모든 결정에 **판단선(threshold)** 을 제시한다.

---

## 무엇을 산출하는가

요청 성격에 따라 세 가지 중 하나 또는 조합을 낸다.

| 요청 유형 | 산출물 |
|---|---|
| 새 기능/앱 설계 | 설계 문서 (결정표 + 데이터 모델 + 흐름도 + 구현 순서) |
| 기술 선택 | 판단 근거 + 선택 + 미선택 조건 |
| 기존 구조 리뷰 | 발견 사항 + 우선순위 + 개선 계획 |
| 구현 착수 | 코드 뼈대 (Android/iOS) + 점검표 |

산출물이 길면 파일로 만들어 `/mnt/user-data/outputs/`에 저장하고 `present_files`로 전달한다. 짧은 결정 하나면 대화로 답한다.

## 워크플로

### 1단계 — 규모를 숫자로 만든다

설계 결정의 대부분이 규모에서 나온다. 사용자가 주지 않으면 물어보거나 가정하고 밝힌다.

```
화면 수:        (지금 / 1년 뒤 예상)
개발자 수:      (지금 / 1년 뒤 예상)
일간 활성 사용자:
쓰기 발생 빈도: (사용자당 하루 몇 건)
오프라인 사용 비중:
민감 데이터 여부: (결제·인증·개인정보)
```

이 여섯 개가 뒤의 거의 모든 판단선에 들어간다. `references/sizing-and-budgets.md`에 규모 추정 방법과 예산 계산이 있다.

### 2단계 — 데이터를 분류한다

기능이 다루는 데이터를 전부 나열하고 두 축으로 분류한다. 이게 저장 위치와 동기화 전략을 정한다.

**축 1 — 원본이 어디 있는가**
- UI 상태: 화면 요소 자체 (스크롤, 입력 중 텍스트)
- 도메인 상태: 앱의 비즈니스 상태 (장바구니, 로그인 사용자)
- 서버 상태: 원본이 서버에 있는 사본 (피드, 프로필)
- 영속 상태: 앱을 꺼도 남아야 함 (토큰, 설정)

**축 2 — 잃으면 어떻게 되는가**
- 잃으면 안 됨: durable 저장 + 순서 + 중복 제거 + 도착 확인
- 잃어도 됨: 저장 안 함 + TTL 만료 + 드롭 허용

두 축을 표로 만들면 저장 위치가 자동으로 정해진다. `references/decision-tables.md`의 1번 표 참고.

### 3단계 — 결정표를 통과시킨다

`references/decision-tables.md`를 열어 해당하는 결정을 순서대로 통과시킨다. 각 표는 **판단선과 그 근거가 되는 계산**을 함께 담고 있다.

주요 결정 목록:
1. 데이터 저장 위치
2. Repository 도입 여부
3. UseCase 도입 여부
4. 아키텍처 패턴 선택
5. 네트워크 계층 중앙화 여부
6. API 프로토콜 선택
7. 캐시 유효기간
8. 오프라인 우선 도입 여부
9. 재시도 정책
10. 실시간 전달 방식
11. 이벤트 처리 방식 (합치기/모으기)
12. 메모리 보안 수준

**결정을 내릴 때마다 미도입 조건도 함께 기록한다.** "지금은 도입하지 않고, 화면이 30개를 넘으면 다시 검토" 같은 형태다. 나중에 재검토 시점이 명확해진다.

### 4단계 — 실패 모드를 점검한다

설계가 정상 경로만 다루면 출시 후에 무너진다. `references/failure-modes.md`의 기능별 점검표를 통과시킨다.

특히 이 다섯 가지는 모든 기능에서 확인한다.

- 네트워크가 없을 때 이 기능은 어떻게 되는가
- 요청이 실패했는데 서버는 처리했을 수 있는가
- 앱이 중간에 종료되면 데이터가 어긋나는 지점이 있는가
- 같은 동작이 두 번 실행되면 무슨 일이 생기는가
- 사용자 100만 명이 동시에 하면 어떻게 되는가

마지막 항목은 개발자 기기 하나로 테스트할 때 절대 안 보인다.

### 5단계 — 구현 순서를 정한다

한 번에 다 만들지 않는다. **읽기 → 쓰기 → 실시간 → 복구** 순서가 대체로 안전하다.

```
1차: 로컬 저장소 + Repository + 화면이 로컬을 관찰
     → 이 단계만으로 화면이 뜰 확률이 크게 올라간다
2차: 쓰기 큐 + 멱등성 키
     → 사용자 입력이 사라지지 않게
3차: 실시간 채널 + 연결 상태 관리
     → 지연을 줄인다
4차: 커서 기반 따라잡기
     → 끊긴 구간을 메운다
```

각 단계가 독립적으로 값을 낸다는 게 중요하다. 1차만 해도 개선이 있고, 2차를 못 해도 1차가 헛되지 않는다.

### 6단계 — 코드 뼈대를 낸다

`references/implementation-patterns.md`에 검증된 패턴이 Android/iOS 짝으로 있다. 필요한 것을 가져와 프로젝트에 맞게 조정한다.

코드를 낼 때 지킬 것:
- Android와 iOS 양쪽을 낸다 (한쪽만 요청받은 게 아니라면)
- 주석은 "무엇을"이 아니라 **"왜 이렇게"**를 적는다
- 함정이 있는 줄에는 함정을 적는다
- 숫자가 나오면 근거를 적는다

## 결정을 기록하는 형식

설계 문서를 만들 때 각 결정을 이 형식으로 적는다. 나중에 "왜 이렇게 했지?"에 답할 수 있어야 한다.

```markdown
### 결정: [무엇을 정하는가]

**선택:** [무엇을 골랐는가]

**근거:**
- 규모: [해당하는 숫자]
- 계산: [판단선과 비교]

**포기한 것:** [이 선택으로 잃는 것]

**재검토 조건:** [어떤 숫자가 바뀌면 다시 볼 것인가]
```

**재검토 조건이 특히 중요하다.** 지금 옳은 결정이 1년 뒤에도 옳다는 보장이 없고, 재검토 시점을 미리 적어 두지 않으면 아무도 다시 보지 않는다.

## 리뷰 모드

기존 코드나 설계를 봐 달라는 요청이면 `references/review-checklist.md`를 쓴다. 발견 사항을 이렇게 분류해서 낸다.

```
지금 고쳐야 함:  데이터 유실·보안 노출·사용자에게 보이는 오동작
곧 고쳐야 함:    규모가 커지면 문제가 되는 것
지켜볼 것:       현재는 괜찮지만 판단선 근처
과한 설계:       지금 규모에 비해 복잡한 것 (제거 후보)
```

**마지막 항목을 빠뜨리지 않는다.** 리뷰가 항상 "더 추가하세요"로 끝나면 코드가 계속 무거워진다. 지금 규모에 과한 구조를 발견하면 걷어낼 것을 제안한다.

## 이 스킬이 피하려는 것

**추상적 조언.** "관심사를 분리하세요", "확장성을 고려하세요" 같은 말은 아무 결정도 내려 주지 않는다. 항상 숫자와 판단선으로 답한다.

**기술 이름 나열.** "Room, Retrofit, Hilt를 쓰면 됩니다"는 설계가 아니다. 왜 그 조합인지, 안 쓰면 무엇이 문제인지가 설계다.

**한 방향 조언.** 도입만 권하고 미도입 조건을 말하지 않으면, 작은 앱이 큰 앱의 구조를 떠안게 된다.

**정상 경로만 설계.** 실패·중복·종료·규모를 점검하지 않은 설계는 출시 후에 다시 만들게 된다.

**완벽 추구.** 모바일 문제의 상당수는 확률과 노출 시간을 줄이는 문제다. 완전한 차단이 불가능한 영역에서 완벽을 목표로 잡으면 아무것도 못 한다. 목표를 정확히 잡는 것 자체가 설계 판단이다.
