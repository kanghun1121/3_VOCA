# 규모 추정과 성능 예산

설계 결정에 넣을 숫자를 만드는 방법이다. 사용자가 값을 주지 않으면 여기 대표값으로 가정하고 그 사실을 밝힌다.

---

## 1. 규모 추정 절차

```
일간 활성 사용자(DAU)
  × 사용자당 하루 동작 수
  = 하루 총 동작 수
  ÷ 86,400
  = 평균 초당 처리량
  × 3
  = 피크 초당 처리량
```

피크 배수 3은 관행적인 값이다. 특정 시간대에 몰리는 서비스(출퇴근, 점심, 저녁 방송)는 5~10으로 잡는다.

**예시 — 메신저**
```
DAU 100만 × 하루 메시지 50건 = 5,000만 건/일
5,000만 ÷ 86,400 ≈ 초당 580건
피크 3배 → 초당 약 1,700건
```

**예시 — 피드 앱**
```
DAU 100만 × 하루 앱 실행 8회 × 화면당 API 5개 = 4,000만 요청/일
4,000만 ÷ 86,400 ≈ 초당 460건
피크 3배 → 초당 약 1,400건
```

이 숫자로 판단하는 것들: 전역 순서 매기기가 가능한지, 연결 유지가 감당되는지, 서버 보관 기간이 얼마나 필요한지.

## 2. 프레임 예산

```
60Hz:  16.6ms
120Hz:  8.3ms
```

한 프레임 안에 배분하는 방식이다.

```
사용자 입력 반응:  최대 8ms
화면 그리기:      최대 5ms
안전 여유:        2ms
──────────────────────
남는 시간:        1.6ms (바쁜 프레임)
                 13.6ms (정지 상태)
```

**활용:** 급하지 않은 작업을 정지 프레임의 남는 시간에 넣는다. 단, 각 작업이 1ms 이내로 쪼개져 있어야 시간 검사가 의미를 갖는다.

**판단:** 어떤 처리가 프레임당 5ms를 넘으면 배칭이나 비동기 처리를 검토한다.

## 3. 메모리 예산

**이미지가 대부분을 차지한다.**

```
비트맵 메모리 = 가로 × 세로 × 픽셀당 바이트

1080 × 1080 × 4 ≈ 4.7MB
 540 ×  540 × 4 ≈ 1.2MB  (가로세로 절반 → 1/4)
```

**캐시 한도:** 앱에 허용된 메모리의 1/8이 관행적인 기준이다. 한도가 256MB면 캐시 32MB.

```
32MB ÷ 4.7MB ≈ 6~7장
32MB ÷ 1.2MB ≈ 26장   ← 디코딩 크기를 줄이면 적중률이 4배
```

**판단:** 캐시를 키우기 전에 항목 크기를 줄인다. 화면에 표시되는 크기보다 큰 해상도로 디코딩하고 있지 않은지 먼저 본다.

**화면별 예산 두기:** 화면마다 메모리 상한을 정하면 문제가 생겼을 때 원인이 즉시 특정된다.

```
목록 화면:   256KB
상세 화면:   512KB (이미지 포함)
결제 화면:    64KB (작고 민감)
```

## 4. 네트워크 예산

**왕복이 지배하는 구간과 크기가 지배하는 구간을 나눈다.**

```
임계 크기 = RTT × 대역폭
         = 0.1초 × 1Mbps ≈ 12.5KB
```

- 10KB 이하: 왕복 횟수를 줄이는 게 효과적
- 100KB 이상: 크기를 줄이는 게 효과적

**계산용 값**
```
셀룰러 RTT:      50~100ms (열악 시 120ms)
TCP + TLS 1.3:   왕복 2회 (신규 연결)
대역폭:          좋음 10Mbps, 나쁨 1Mbps
요청 실패율:      조건 좋음 1%, 이동 중 3~5%
```

**데이터 요금 관점도 함께 본다.**
```
요청당 1KB 절약 × 하루 500요청 = 500KB/일 = 약 15MB/월
```

시간으로는 무시할 수준이어도 데이터 요금이 비싼 지역에서는 의미가 있다.

## 5. 배터리 예산

**셀룰러 라디오가 가장 큰 항목이다.**

```
전송 후 고전력 유지 시간(tail): 10~20초 (계산용 15초)
```

폴링 주기별 라디오 가동률:

```
60초 주기: 15/60 = 25%
30초 주기: 15/30 = 50%
15초 주기: 100%
 5초 주기: 100%   ← 15초와 배터리가 같은데 요청만 3배
```

**판단:** 주기가 tail time보다 짧아질 것 같으면 연결 유지 방식으로 바꾼다.

**요청 모으기:** 앱에 주기 작업이 3개 있으면 같은 시점에 실행되게 모은다. 라디오를 한 번만 깨우면 되므로 요청 수는 같아도 배터리가 달라진다.

## 6. 저장 예산

```
메시지·게시물 1건 (텍스트+메타): 약 2KB
이미지 파일 1장:                200~500KB
```

```
텍스트 1만 건    = 20MB      ← 감당 가능
이미지 1천 장    = 300MB     ← 선별 필요
```

**판단:** 텍스트는 최근 수천~수만 건을 통째로 갖고 있어도 된다. 미디어는 최근 본 것과 곧 볼 것으로 제한한다.

**서버 보관 기간:** 클라이언트가 영구 저장을 맡으면 서버는 미전달 분만 보관하면 된다. 보관 기간별로 전체 재동기화가 필요한 사용자 비율을 보고 정한다. 대체로 7일 근처에서 추가 보관의 효과가 급격히 줄어든다.

## 7. 서버 측 규모 감각

클라이언트 설계에도 영향을 주는 값들이다.

```
WebSocket 연결당 메모리:      2~64KB (구현에 따라)
서버당 초당 신규 TLS 연결:     약 2,000 (계산용)
단일 서버 동시 연결 (실사례):   100만~280만
```

**재연결 폭주 계산 예시**
```
서버 100대 × 초당 2,000 = 초당 20만 연결 처리 가능
100만 연결을 복구하려면 최소 5초

→ 즉시 재시도하면 첫 순간에 100만이 몰려 복구가 안 된다
→ 첫 재연결을 0~5초에 분산하면 초당 20만이 되어 처리 범위 안
```

## 8. 값을 제시할 때의 규칙

**대표값임을 밝힌다.** "정확한 값은 기기와 망 상태에 따라 다르니 자릿수만 보시면 됩니다."

**계산 과정을 보인다.** 결과만 던지지 않는다.

**결과에 의미를 붙인다.** "91.3%"가 아니라 "100번 중 9번은 화면이 제대로 안 뜹니다. 하루 20번 앱을 열면 이틀에 한 번꼴입니다."

**측정으로 대체할 수 있으면 측정한다.** 대표값은 자릿수 감각용이고, 실제 결정은 자기 앱의 실측값으로 하는 게 정확하다. 어떤 값을 측정해야 하는지 함께 알려준다.
