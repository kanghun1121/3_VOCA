## 1. 데이터 저장 위치

세 질문으로 정한다.

```
Q1. 앱 프로세스가 죽으면 사라져도 되는가? → 안 되면 디스크
Q2. 원본을 서버가 갖고 있는가?           → 그렇다면 유효기간 관리 필요
Q3. 화면을 벗어나도 의미가 있는가?        → 없으면 화면 컴포넌트에
```

| 데이터 | 메모리 캐시 | 디스크 | 유효기간 | 비고 |
|---|---|---|---|---|
| 목록·상세 (서버 원본) | ○ | 로컬 DB | ○ | 화면은 DB를 관찰 |
| 이미지·동영상 | ○ | 캐시 디렉터리 | △ | 다시 받을 수 있으므로 |
| 검색 결과 | △ | 저장 안 함 | ○ | 재사용 확률이 낮음 |
| 인증 토큰 | × | Keychain / 암호화 저장 | × | 메모리 사본을 늘리지 않음 |
| 사용자 설정 | × | DataStore / UserDefaults | × | 로컬 원본 |
| 작성 중 초안 | × | Documents / DB | × | 다시 만들 수 없음 |
| 스크롤 위치 | ○ | 저장 안 함 | × | 화면 수명 |
| 온라인 표시·입력 중 | 메모리 + TTL | 저장 안 함 | 만료로 처리 | 잃어도 됨 |

**근거:** 계층별 접근 시간이 자릿수로 메모리 1 : 디스크 1,000 : 네트워크 1,000,000이다. 그리고 서버 상태와 로컬 상태를 같은 저장소에 섞으면 유효기간 정책을 하나만 적용하게 되어 한쪽이 반드시 어긋난다.

**주의:** 다시 만들 수 있는 파일을 백업 대상 디렉터리에 두지 않는다. 사용자의 백업 용량을 쓰고 저장 공간이 부족해도 정리되지 않는다.

## 2. Repository 도입

```
도입: 이 데이터를 쓰는 화면이 2개 이상  OR  데이터 출처가 2개 이상
미도입: 화면 1개 + 출처 1개
```

**근거:** 서버 응답 형식이 바뀌었을 때 고칠 파일 수가 화면 수만큼에서 1개로 줄어든다. 화면이 8개면 12~15개 파일이 1개가 된다. 화면이 1개면 파일 두 개를 더 만들고 얻는 게 1배라 손해다.

**출처가 2개 이상이면 화면 수와 무관하게 도입한다.** 여러 출처를 조율하는 코드가 어딘가에는 있어야 하는데, ViewModel에 넣으면 화면이 데이터 접근 방식을 알게 된다.

## 3. UseCase 도입

Repository와 **따로 판단한다.** 둘을 한 세트로 묶는 것이 과한 구조의 흔한 원인이다.

```
도입: 다음 중 하나에 해당
  ① 여러 Repository를 조합해야 하고, 그 조합을 쓰는 화면이 2개 이상
  ② 화면과 무관한 비즈니스 규칙이 있음 (차단 사용자 필터링 등)
  ③ 팀이 커서 데이터 계층과 화면 계층 사이에 변경 차단이 필요

미도입: 셋 다 아니면 ViewModel이 Repository를 직접 호출
```

**근거:** UseCase 하나의 비용은 파일 1개와 주입 설정. Repository를 그대로 넘기기만 하는 UseCase는 위 세 조건 중 ③에 해당할 때만 값을 한다. Google 공식 아키텍처 가이드도 domain layer를 선택 사항으로 둔다.

## 4. 아키텍처 패턴

세 숫자로 정한다.

```
질문 1: 화면 10개 이하 AND 개발자 1~2명인가?
  → 예: MVVM 가볍게 (상태는 sealed 타입, 계층 최소)

질문 2: 한 화면의 독립적인 상태 값이 5개 이상 얽혀 있는가?
  → 아니오: MVVM + 단일 상태 타입 (대부분의 앱)
  → 예: MVI / TCA (Intent로 변경 통로 통일, 상태 변경 로그 확보)

질문 3: 화면 흐름이 조건 분기로 복잡한가? (7단계 예약, 온보딩 분기)
  → 예: 화면 전환을 별도 컴포넌트로 분리
```

**근거 1 — 파일 수:** 화면당 파일이 MVC 2개, MVVM 3개, MVI 4~5개, VIPER 5~6개. 화면 50개면 100개 대 300개로 200개 차이가 난다.

**근거 2 — 상태 조합:** 독립적인 참/거짓 값 3개면 조합이 8가지인데 정상은 4가지다. 값이 8개면 256가지 중 대부분이 정의되지 않은 상태다. 단일 sealed 타입으로 묶으면 표현 가능한 상태 수가 정상 상태 수와 같아진다.

**근거 3 — 팀 규모:** 화면당 파일이 1개면 레이아웃 작업자와 로직 작업자가 같은 파일을 편집한다. 개발자 2명이면 드물지만 12명이면 매일 충돌한다.

**중요:** 앱 전체를 한 패턴으로 통일할 필요가 없다. 설정 화면과 편집 화면의 답이 다른 게 정상이다.

## 5. 네트워크 계층 중앙화

```
도입: 화면 3개 이상 AND 인증이 있음
미도입: 프로토타입, 인증 없음, 서드파티 SDK 통신
```

**근거:** 횡단 관심사(인증 헤더·공통 헤더·직렬화·에러 매핑·재시도·타임아웃·로깅) 7개 × 호출 지점 n개가 관리 대상이 된다. 각 지점이 99% 정확해도 화면 40개면 0.99^280 ≈ 6%다. 중앙화하면 0.99^7 ≈ 93%.

**반드시 포함할 것:**
- 토큰 갱신 single-flight (없으면 병렬 요청이 동시에 401을 받아 갱신이 여러 번 나가고, 리프레시 토큰이 일회용이면 대부분 실패해 사용자가 로그아웃된다)
- 갱신 요청 자체는 인증 인터셉터를 건너뛰게 (무한 반복 방지)
- 앱 버전 헤더 (나중에 필드 제거 판단의 유일한 근거)
- 클라이언트 하나를 공유 (연결 풀 재사용, TCP+TLS 왕복 2회 절약)

## 6. API 프로토콜

```
Q1. 외부 공개 / 서드파티가 쓰는가?
  → 예: REST (표준, HTTP 캐싱 그대로)

Q2. 화면 하나에 필요한 데이터가 여러 자원에 흩어져 있는가? (요청 3개 이상)
  → 예: GraphQL 검토
  → 아니오: REST 유지

별도 축: 응답이 100KB를 넘거나 스트리밍이 필요하면 gRPC 검토
```

**근거 1 — 크기 임계점:** 전송 시간이 왕복 시간과 같아지는 크기는 대략 `RTT × 대역폭`. RTT 100ms, 1Mbps면 약 12.5KB. **10KB 이하에서는 형식을 바꿔 크기를 절반으로 줄여도 전체 시간의 1% 정도만 줄어든다.**

**근거 2 — 왕복 수:** 화면 하나에 요청 7개, 각 97% 성공이면 화면이 온전할 확률이 0.97⁷ ≈ 81%. GraphQL로 1회면 97%.

**GraphQL로 잃는 것 (반드시 계산에 포함):**
- HTTP 캐싱을 그대로 쓸 수 없음 (단일 주소 POST)
- 서버 로그에 주소가 하나만 찍혀 관찰이 어려움
- 쿼리 조합에 따라 서버 비용 예측이 어려움

**모바일 고유:** 시간이 아니라 데이터 요금으로 보면 결론이 달라질 수 있다. 하루 500요청 × 935바이트 = 467KB, 한 달 14MB.

## 7. 캐시 유효기간

```
유효기간 = 허용 오류율 × 평균 변경 간격

단, 순서가 있다:
  1. 틀렸을 때의 피해를 먼저 본다
  2. 피해가 크면 유효기간을 줄이는 게 아니라 쓰는 시점에 서버 확인
```

| 데이터 | 변경 간격 | 피해 | 전략 | 유효기간 |
|---|---|---|---|---|
| 피드 목록 | 수 분 | 낮음 | 낡은 값 즉시 표시 + 뒤에서 갱신 | 5분 |
| 좋아요 수 | 수 초 | 낮음 | 낡음 허용, 내 행동은 즉시 반영 | 1분 |
| 프로필 | 수십 일 | 낮음 | 긴 유효기간 + 조건부 요청 | 6시간 |
| 상품 가격(목록) | 수 시간 | 중간 | 짧은 유효기간 | 1분 |
| 상품 가격(결제) | — | 높음 | **캐시 사용 안 함, 서버 확인** | 없음 |
| 재고 | 수 초 | 높음 | 캐시 사용 안 함 | 없음 |
| 잔액 | 수 시간 | 높음 | 화면 진입 시마다 갱신 | 없음 |

**반드시 할 것:** 유효기간에 ±20% 무작위를 섞는다. 모든 기기가 같은 값을 쓰면 만료 시점이 겹쳐 서버에 순간적으로 몰린다. 100만 건이 한 순간에 오는 것과 2초에 퍼지는 것의 차이다.

**저장 시 함께 기록:** 받아온 시각(`fetchedAt`)과 서버가 준 데이터 지문(`etag`). 없으면 신선도 판단 자체가 불가능하다.

## 8. 오프라인 우선

```
도입: 사용자가 데이터를 만들어 내고 그게 사라지면 안 됨
      OR 네트워크가 불안정한 환경에서 많이 쓰임
      OR 앱을 여는 즉시 내용이 보여야 함

미도입: 데이터가 항상 최신이어야만 의미가 있음 (시세, 경매)
        서버 승인이 있어야 완료되는 작업 (결제, 예약 확정, 재고 차감)
        조회만 하고 사용자가 만드는 데이터가 없음
```

**근거:** 화면 하나에 API 3개, 각 3% 실패면 화면이 제대로 뜰 확률이 0.97³ ≈ 91.3%. 로컬을 먼저 읽으면 100%가 되고, 네트워크 실패가 "화면이 안 뜸"에서 "데이터가 조금 오래됨"으로 바뀐다.

**단계적 도입이 가능하다.** 읽기만 먼저 로컬 우선으로 바꿔도 위 확률 개선을 얻는다. 쓰기 큐는 그다음에 필요한 기능부터.

**저장 비용:** 텍스트는 싸고 미디어는 비싸다. 게시물 1만 건 텍스트 = 20MB인데 이미지까지면 300MB. **텍스트는 아낌없이, 미디어는 선별해서.**

## 9. 재시도 정책

```
재시도 가능 = (일시적 오류인가?) AND (두 번 보내도 안전한가?)

기본값은 "재시도 안 함". 안전한 것만 켠다.
```

| 실패 | 재시도 | 비고 |
|---|---|---|
| 네트워크 오류 | ○ | 일시적일 가능성 높음 |
| 408, 429 | ○ | 429는 서버가 준 대기 시간 우선 |
| 5xx | ○ | 서버 일시적 문제 |
| 400, 401, 403, 404, 422 | × | 다시 보내도 결과가 같음 |

**요청 종류별 정책 분리:**

```
화면에서 기다리는 요청:  총 예산 5초, 재시도 1회
백그라운드 동기화:      총 예산 10분, 재시도 6회
멱등성 키 없는 변경:    재시도 없음
```

**근거 1 — 증폭:** 총 요청 배수 = `1 + p + p² + ... + pⁿ`. 실패율 1%면 1.01배지만 80%면 2.95배. **서버가 힘들 때 부하를 3배로 올리는 구조**라 원인을 제거해도 회복이 안 된다.

**근거 2 — 사용자 인내:** 타임아웃 2초 + 재시도 3회 + 백오프면 총 15초. 사용자는 그 전에 떠난다. 그래서 재시도 횟수를 먼저 정하지 말고 **총 예산에서 역산**한다.

**타임아웃:** 정상 응답 p99보다 넉넉하게(1.5~2배), 사용자 인내보다는 짧게. p50 근처로 잡으면 멀쩡한 서버에 스스로 부하를 만든다.

**반드시 포함:** 간격에 무작위 요소(계산값의 50~100%), 최대 재시도 상한, 재시도 예산(전체 요청의 10%), 회로 차단기(엔드포인트 단위).

## 10. 실시간 전달 방식

```
Q1. 허용 지연이 몇 분 이상인가? → 폴링 (단, 주기는 15초 이상)
Q2. 서버 → 클라이언트 단방향인가? → SSE
Q3. 양방향이고 클라이언트도 자주 보내는가? → WebSocket
```

| 방식 | 평균 지연 | 하루 요청/기기 | 방향 | 재연결 복구 |
|---|---|---|---|---|
| 폴링 | 주기의 1/2 | 86,400/주기 | 클라→서버 | 해당 없음 |
| 롱 폴링 | 거의 없음 | 이벤트 수 + 타임아웃 | 서버→클라 | 직접 구현 |
| SSE | 거의 없음 | 1회 | 서버→클라 | **표준에 포함** |
| WebSocket | 거의 없음 | 1회 | 양방향 | 직접 구현 |

**근거 1 — 곱이 상수:** 폴링의 `평균 지연 × 하루 요청 수 = 43,200`. 주기를 어떻게 잡아도 이 곱은 안 바뀐다. 곡선을 벗어나려면 방식을 바꿔야 한다.

**근거 2 — 라디오:** 셀룰러 라디오는 전송 후 10~20초 동안 고전력을 유지한다. **폴링 주기가 이보다 짧으면 라디오가 계속 켜져 있는 것과 같다.** 15초 주기와 5초 주기의 배터리 소모가 거의 같고 요청만 3배다.

**주의:** Android는 백그라운드 반복 작업의 최소 주기가 15분이다. 짧은 주기 폴링은 선택지가 아니다.

**연결 관리 필수 항목:**
- 하트비트 30~45초 (아래로는 라디오 tail time, 위로는 중간 장비 유휴 정리)
- 앱이 화면으로 돌아오면 기존 연결을 신뢰하지 않고 3~5초 시한으로 재확인
- 재연결 **첫 시도부터** 무작위 지연 (대량 절단 시 끊긴 순간이 이미 동기화되어 있음)
- 연결 상태를 명시적 타입으로 두고 앱 전체가 하나를 구독

**실시간 채널은 정확성을 책임지지 않는다.** 정확성은 커서 기반 동기화가 맡는다. 재연결·앱 복귀·순번 건너뜀 감지 시 동기화를 돌린다.

## 11. 이벤트 처리 방식

들어오는 이벤트가 처리 속도보다 빠를 때.

```
Q1. 화면에 보이지 않는 대상인가? → 구독하지 않는다 (가장 효과 큼)
Q2. 각 항목이 독립적인 의미를 갖는가?
  → 예 (메시지·주문·로그): 모으기 + 버퍼 초과 시 대기
  → 아니오 (시세·위치·진행률): 합치기 + 버퍼 초과 시 오래된 것 버리기

공통: 화면 갱신은 프레임당 1회로 제한
```

**합치기와 모으기를 구분하는 것이 핵심이다.** 합치기는 정보를 줄이고 모으기는 정보를 유지한다. 채팅에 합치기를 쓰면 메시지가 사라지는데, 시세에 모으기를 쓰면 성능 개선이 덜 될 뿐이다. **틀렸을 때의 피해가 비대칭이라 확신이 없으면 모으기를 쓴다.**

**근거:** 이벤트 1건 처리에 항목별 비용 0.4ms + 고정 비용 1.7ms라면, 17건을 개별 처리하면 35.7ms로 프레임 예산을 넘기고 묶으면 8.5ms로 들어온다.

**측정부터:** 수신 시각과 화면 반영 시각의 차이를 기록한다. **지연이 일정하면 느린 것이고, 계속 커지면 대기열이 자라는 중**이라 대응이 필요하다.

## 12. 메모리 보안 수준

```
1단계 (비용 거의 없음 — 민감 데이터가 있으면 무조건):
  - 앱이 백그라운드로 갈 때 민감 값 정리
  - 화면 이탈 시 입력 위젯 비우기
  - 로그·크래시 리포트에 민감 값이 안 나가게 (description 재정의)
  - 화면 캡처 방지

2단계 (비용 있음 — 카드번호·비밀번호·개인키·인증 토큰에만):
  - 전용 보안 버퍼 타입 (직접 할당한 원시 버퍼 + 해제 훅)
  - 값을 반환하지 않고 클로저 안에서만 접근
  - 최적화로 제거되지 않는 제로화 함수
  - 커스텀 보안 키패드 (문자열을 아예 안 만듦)

0단계 (가능하면 이것부터):
  - 그 데이터를 아예 받지 않는다 (결제 사업자 화면 위임, 토큰 대체)
  - 키는 시스템 저장소에 맡긴다 (Keychain / Keystore / StrongBox)
```

**근거:** 값 하나가 입력 위젯·문자열 객체·직렬화 버퍼·암호화 전 버퍼까지 아홉 군데 사본을 만들고 절반은 통제할 수 없다. **완전한 제거는 불가능하므로 목표를 노출 시간 최소화로 잡는다.** 30분에서 0.2초로 줄이면 노출 확률이 수천 배 낮아진다.

**함정:** 일반 `memset`은 "이후 아무도 읽지 않으므로 결과에 영향 없음"으로 판단되어 컴파일러가 제거할 수 있다. `memset_s` 같은 최적화 제외 함수를 쓴다.
