# 실패 모드 점검표

설계가 정상 경로만 다루면 출시 후에 다시 만들게 된다. 기능을 설계할 때 해당 절을 통과시킨다.

---

## 공통 다섯 질문

모든 기능에 적용한다.

```
1. 네트워크가 없을 때 이 기능은 어떻게 되는가
2. 요청이 실패했는데 서버는 처리했을 수 있는가
3. 앱이 중간에 종료되면 데이터가 어긋나는 지점이 있는가
4. 같은 동작이 두 번 실행되면 무슨 일이 생기는가
5. 사용자 100만 명이 동시에 하면 어떻게 되는가
```

5번이 특히 중요하다. 개발자 기기 하나로 테스트할 때 절대 보이지 않고, 출시 후 규모가 커져야 나타난다.

---

## 화면과 상태

| 실패 모드 | 증상 | 확인 |
|---|---|---|
| 회전·프로세스 종료로 입력 소실 | 사용자가 다시 입력 | 복원돼야 할 값에만 저장 비용을 쓰는가 |
| 화면 간 상태 불일치 | 탭마다 다른 값 | 같은 데이터를 두 곳 이상이 각자 들고 있지 않은가 |
| 정의되지 않은 상태 조합 | 로딩과 에러가 동시에 표시 | 상태가 여러 독립 값으로 흩어져 있지 않은가 |
| 불필요한 재계산 | 스크롤 버벅임 | 고빈도 값이 전역 알림을 발생시키지 않는가 |

---

## 네트워크 요청

| 실패 모드 | 증상 | 확인 |
|---|---|---|
| 토큰 갱신 경쟁 | 이유 없는 로그아웃 | 갱신이 동시에 여러 번 실행될 수 있는 구조가 아닌가 |
| 갱신 무한 반복 | 앱 멈춤, 서버에 초당 수십 요청 | 갱신 요청이 인증 인터셉터를 건너뛰는가 |
| 재시도 증폭 | 장애가 회복되지 않음 | 백오프·무작위·상한·예산이 모두 있는가 |
| 재시도 중복 | 결제·댓글 중복 | 멱등성 키 없는 변경 요청이 자동 재시도되지 않는가 |
| 재시도 곱하기 | 예상보다 많은 요청 | 라이브러리 내장 재시도와 우리 재시도가 겹치지 않는가 |
| 타임아웃 과소 | 멀쩡한 서버에 부하 | 타임아웃이 정상 응답 p99보다 넉넉한가 |
| 사용자 이탈 후 요청 | 낭비 | 화면 요청의 총 시간 예산이 5초 이내인가 |

**공통 원인:** 요청이 실패한 것과 서버가 처리하지 않은 것을 구분하지 않으면 위 항목 중 여러 개가 동시에 발생한다.

## API 진화

| 실패 모드 | 증상 | 확인 |
|---|---|---|
| 열거형 값 추가 | 목록 화면 전체가 빔 | 모르는 값을 견디는 처리가 있는가 |
| 필드 삭제 | 구버전 앱 크래시 | 삭제 대신 병행 기간을 두는가 |
| 비옵셔널 필드 누락 | 응답 전체 디코딩 실패 | 사라질 수 있는 필드가 옵셔널인가 |
| 항목 하나가 전체를 막음 | 목록이 비어 보임 | 항목 단위 디코딩 실패를 견디는가 (그리고 버린 개수를 보고하는가) |
| 제거 시점 판단 불가 | 영영 못 지움 | 요청에 앱 버전이 실려 나가는가 |

**핵심:** 필드 추가는 안전하지만 열거형 값 추가는 안전하지 않다. 이미 배포된 앱의 파싱 동작은 나중에 고칠 수 없으므로 처음부터 방어한다.

## 오프라인과 동기화

| 실패 모드 | 증상 | 확인 |
|---|---|---|
| 데이터만 저장, 큐 누락 | 영영 전송 안 됨 | 데이터 저장과 전송 기록이 한 트랜잭션인가 |
| 커서를 먼저 갱신 | 구간이 조용히 사라짐 | 저장 후에 커서를 갱신하는가, 같은 트랜잭션인가 |
| 전송 중 상태로 멈춤 | 특정 항목만 안 감 | 앱 시작 시 멈춘 항목을 되살리는가 |
| 전송 상태 미표시 | 사용자가 보냈다고 착각 | 대기·완료·실패 3상태가 화면에 있는가 |
| 실패 후 방치 | 내용까지 사라짐 | 최종 실패 시 내용을 보존하고 재시도 수단을 주는가 |
| 대화방마다 개별 요청 | 재접속이 느림 | 커서를 묶어 한 번에 보내는가 |
| 보관 기간 초과 | 복구 불가 | 초과 시 스냅샷 경로가 따로 있는가 |

**순서 판단 기준:** 둘 중 하나만 실행됐을 때 어느 쪽이 덜 나쁜지를 본다. 중복을 받는 것이 데이터를 잃는 것보다 낫다.

## 실시간 연결

| 실패 모드 | 증상 | 확인 |
|---|---|---|
| 죽은 연결을 살아 있다고 믿음 | 메시지가 조용히 안 옴 | 하트비트와 응답 시한이 있는가 |
| 백그라운드 복귀 후 신뢰 | 복귀 직후 수신 안 됨 | 화면 복귀 시 짧은 시한으로 재확인하는가 |
| 네트워크 전환 미감지 | 수 분간 먹통 | 상태 변경 알림을 구독하는가 |
| 재연결 폭주 | 서버가 복구 못 함 | 첫 시도부터 무작위 지연이 있는가 |
| 하트비트 과다 | 배터리 소모 | 간격이 20초 이상인가 |
| 하트비트 과소 | 중간 장비가 연결 정리 | 간격이 60초 이하인가 |
| 연결만 복구 | 끊긴 동안 데이터 없음 | 재연결 후 동기화를 돌리는가 |
| 연결 방치 | 서버 비용 | 화면을 벗어나면 닫는가 |

## 메시지 순서와 중복

| 실패 모드 | 증상 | 확인 |
|---|---|---|
| 경로별 개별 처리 | 특정 경로만 중복 처리 누락 | 모든 수신 경로가 하나의 진입점을 통과하는가 |
| 메모리 집합으로만 중복 판정 | 앱 재시작 직후 중복 | DB 기본키로 판정하는가 |
| 도착 순서로 표시 | 순서 뒤바뀜 | 화면이 순번 순으로 읽는가 |
| 빠진 항목 무한 대기 | 그 뒤 전부 안 보임 | 최대 대기 시간이 있는가 |
| 기기 시계로 정렬 | 나중 것이 먼저 표시 | 서버 시각이나 순번을 쓰는가 |

## 휘발성 데이터 (온라인 표시, 입력 중)

| 실패 모드 | 증상 | 확인 |
|---|---|---|
| 종료 신호 의존 | 표시가 영원히 남음 | 시간 기준 만료가 있는가 |
| 타건마다 전송 | 서버 부하 | 발신 억제 간격이 있는가 |
| 전원 구독 | 큰 채널에서 감당 불가 | 화면에 보이는 대상만 구독하는가 |
| durable 저장 | DB 쓰기 폭증 | 메모리 + TTL로 처리하는가 |
| 모름을 오프라인으로 표시 | 스크롤할 때마다 회색 | 온라인·오프라인·모름 3상태를 구분하는가 |

**규모 주의:** 이벤트 수가 채널 크기의 제곱으로 늘어난다. 작은 대화방에서 잘 되던 구현이 큰 채널에서는 다른 방식이 필요하다.

## 이벤트 처리와 렌더링

| 실패 모드 | 증상 | 확인 |
|---|---|---|
| 이벤트마다 DB 쓰기·렌더 | 화면 멈춤 | 프레임 단위로 모으는가 |
| 독립 항목에 합치기 적용 | 데이터 소실 | 합쳐도 되는 데이터인지 확인했는가 |
| 마지막 값 유실 | 진행률이 99%에서 멈춤 | 흐름 종료 시 남은 값을 내보내는가 |
| 사용자 입력에 억제 | 버튼이 안 눌리는 느낌 | 사용자 직접 행동은 즉시 반영하는가 |
| 무한 증가하는 대기열 | 메모리 증가 후 종료 | 수신·반영 시각 차이를 측정하는가 |

## 푸시 알림

| 실패 모드 | 확인 |
|---|---|
| 푸시 데이터를 그대로 저장 | 동기화로 확인하는가 |
| 토큰 갱신 누락 | 토큰 변경 시 서버에 등록하는가 |
| 메시지에 대체 식별자 사용 | 중간 항목이 사라지지 않는가 |
| 앱 실행 시 동기화 없음 | 푸시를 못 받은 경우의 유일한 복구 경로가 있는가 |
| 크기 초과 | 4KB 한도 안에 들어가는가 (암호화 시 인코딩으로 증가) |
| 조용한 푸시 남용 | 하루 수십 건 상한을 넘지 않는가 |

**전제:** 푸시는 전달이 보장되지 않는다. 관문 다섯 개(권한·토큰·플랫폼 전달·기기 수신·앱 실행)를 곱하면 도달률이 크게 떨어진다. **데이터 전달이 아니라 깨우기 신호로 쓴다.**

## 메모리 보안

| 실패 모드 | 확인 |
|---|---|
| 문자열로 변환 | 민감 값에 `toString()`을 호출하지 않는가 |
| 최적화로 제거되는 제로화 | 전용 함수를 쓰는가 |
| 지우기 전에 메모리 반환 | 해제 훅 안의 순서가 맞는가 |
| 해제 훅 미호출 | 참조 순환이 없는가 (디버그 로그로 확인) |
| 새 값이 짧아 옛 값 잔존 | 쓰기 시작에 전체를 0으로 채우는가 |
| 로그·크래시 리포트 노출 | 문자열 표현을 가린 값으로 정의했는가 |
| 백그라운드 방치 | 앱 상태 전환 시 정리하는가 |
| 검증 없음 | 평문이 남지 않는지 자동으로 확인하는가 |

## 자원 수명

| 실패 모드 | 확인 |
|---|---|
| 긴 수명이 짧은 수명을 참조 | 세션 객체가 화면 자원을 붙잡고 있지 않은가 |
| 프레임 자원을 하나씩 관리 | 반복 생성되는 임시 객체를 묶어서 처리하는가 |
| 재사용 전 미정리 | 버퍼를 돌려쓸 때 이전 내용을 지우는가 |
| 화면 이탈 후 구독 유지 | 보이지 않는 화면의 데이터를 계속 처리하지 않는가 |

## 점검 결과를 쓰는 방법

발견한 항목을 이렇게 분류한다.

```
지금 고쳐야 함:  데이터 유실·보안 노출·사용자에게 보이는 오동작
곧 고쳐야 함:    규모가 커지면 문제가 되는 것
지켜볼 것:       현재 괜찮지만 판단선 근처
```

그리고 각 항목에 **재현 조건**을 적는다. 대부분의 실패 모드는 특정 조건에서만 나타나서, 조건을 모르면 수정 후 확인할 수가 없다.
