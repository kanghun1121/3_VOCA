# 리뷰 체크리스트

기존 코드나 설계를 검토할 때 쓴다. 순서대로 훑고, 발견 사항을 네 등급으로 분류한다.

---

## 결과 분류

```
지금 고쳐야 함:  데이터 유실 · 보안 노출 · 사용자에게 보이는 오동작
곧 고쳐야 함:    규모가 커지면 문제가 되는 것
지켜볼 것:       현재는 괜찮지만 판단선 근처
과한 설계:       지금 규모에 비해 복잡한 것 (제거 후보)
```

**마지막 등급을 빠뜨리지 않는다.** 리뷰가 항상 추가로 끝나면 코드가 계속 무거워진다. 지금 규모에 과한 구조를 발견하면 걷어낼 것을 제안한다.

각 발견 사항에 **재현 조건**을 함께 적는다. 조건을 모르면 수정 후 확인할 수가 없다.

---

## 1. 상태와 화면

- [ ] 서버에서 온 데이터를 화면 컴포넌트가 직접 소유하고 있지 않은가
- [ ] 같은 데이터를 두 곳 이상의 ViewModel이 각자 변수로 들고 있지 않은가
- [ ] 화면 상태가 여러 독립 값으로 흩어져 정의되지 않은 조합이 만들어질 수 있지 않은가
- [ ] UI 코드에 상태를 직접 대입하는 문장이 있지 않은가
- [ ] Loading과 Error가 예외 처리가 아니라 상태 타입에 들어 있는가
- [ ] 초당 수십 번 바뀌는 값이 전역 알림을 발생시키지 않는가
- [ ] 회전·프로세스 종료 후 복원돼야 할 값에만 저장 비용을 쓰는가

---

## 2. 계층 구조

- [ ] UI/ViewModel 코드에 HTTP 타입이 등장하지 않는가 (`Response`, 상태 코드, HTTP 예외)
- [ ] domain 코드에 프레임워크 타입이 들어와 있지 않은가
- [ ] Repository가 있는데 화면 수 1개 + 출처 1개는 아닌가 **(과한 설계 후보)**
- [ ] 그냥 Repository를 넘기기만 하는 UseCase가 몇 개인가 **(과한 설계 후보)**
- [ ] 반대로, 같은 데이터 접근 코드가 여러 화면에 복사돼 있지 않은가
- [ ] 화면 없이 로직만 확인하는 테스트가 실제로 돌고 있는가

---

## 3. 네트워크

- [ ] 앱 전체가 하나의 HTTP 클라이언트를 공유하는가 (연결 풀 재사용)
- [ ] 공통 헤더를 추가할 때 고쳐야 할 파일이 하나인가
- [ ] 모든 요청에 앱 버전이 실려 나가는가
- [ ] 토큰 갱신이 동시에 여러 번 실행될 수 있는 구조가 아닌가
- [ ] 갱신 요청 자체가 인증 경로를 건너뛰는가
- [ ] 네트워크 오류로 인한 갱신 실패와 서버 거부를 구분하는가
- [ ] 401 재시도가 일반 재시도 카운터를 쓰고 있지 않은가
- [ ] 재시도 정책이 요청 종류별로 다른가
- [ ] 멱등성 키 없는 변경 요청이 자동 재시도되고 있지 않은가
- [ ] 재시도 간격에 무작위 요소가 있는가
- [ ] 라이브러리 내장 재시도와 우리 재시도가 곱해지고 있지 않은가 (실제 횟수를 세어 볼 것)
- [ ] 타임아웃이 정상 응답 p99보다 넉넉한가
- [ ] 화면에서 기다리는 요청의 총 시간 예산이 5초 이내인가

---

## 4. API 진화

- [ ] 응답 모델의 열거형이 모르는 값을 견디는가
- [ ] 목록 응답에서 항목 하나의 디코딩 실패가 전체를 비우지 않는가
- [ ] 버린 항목 개수를 기록하는가
- [ ] 사라질 수 있는 필드가 옵셔널로 선언돼 있는가
- [ ] 필드 제거 전에 병행 기간과 사용량 측정이 있는가
- [ ] 서버 코드에 앱 버전 비교 조건문이 다섯 개를 넘지 않는가

---

## 5. 저장과 캐시

- [ ] 서버에서 온 데이터와 사용자 설정이 같은 저장소에 섞여 있지 않은가
- [ ] 저장한 데이터에 받아온 시각이 함께 기록되고 있는가
- [ ] 유효기간이 데이터마다 다르게 정해져 있는가 (전체 동일이면 근거가 없는 것)
- [ ] 유효기간에 무작위 요소가 섞여 있는가
- [ ] 결제 금액이나 재고처럼 틀리면 곤란한 값에 캐시가 쓰이고 있지 않은가
- [ ] 메모리 캐시가 항목 개수가 아니라 크기 합계로 관리되는가
- [ ] 화면에 표시되는 크기보다 큰 해상도로 이미지를 디코딩하고 있지 않은가
- [ ] 다시 받아올 수 있는 파일이 백업 대상 디렉터리에 저장되고 있지 않은가

---

## 6. 오프라인과 동기화

- [ ] 화면이 서버 응답을 기다린 뒤에야 그려지고 있지 않은가
- [ ] 사용자가 만든 데이터가 서버 전송 전에 로컬에 저장되는가
- [ ] 데이터 저장과 전송 기록이 하나의 트랜잭션 안에 있는가
- [ ] 커서 갱신이 데이터 저장 후에, 같은 트랜잭션 안에서 일어나는가
- [ ] 전송 중 상태로 멈춘 항목을 앱 시작 시 되살리는가
- [ ] 대기·완료·실패 상태가 화면에 표시되고 실패에 다시 시도 수단이 있는가
- [ ] 최종 실패 시 내용을 보존하는가 (조용히 삭제하지 않는가)
- [ ] 동기화 트리거가 여러 개인데 전부 같은 함수를 부르는가
- [ ] 동기화 중복 실행이 막혀 있는가
- [ ] 대화방마다 따로 요청하지 않고 커서를 묶어 보내는가

---

## 7. 실시간 연결

- [ ] 연결 상태가 명시적 타입으로 있고 앱 전체가 하나를 구독하는가
- [ ] 하트비트 간격이 20초 이상 60초 이하인가
- [ ] 응답 시한이 있는가 (없으면 죽은 연결을 감지하지 못한다)
- [ ] 앱이 화면으로 돌아왔을 때 기존 연결을 확인 없이 신뢰하고 있지 않은가
- [ ] 네트워크 상태 변경을 구독하는가
- [ ] 재연결 첫 시도에 무작위 지연이 있는가
- [ ] 재연결 후 동기화를 돌리는가 (연결 복구와 데이터 복구는 다르다)
- [ ] 화면을 벗어나면 연결을 정리하는가
- [ ] (iOS) `receive` 재귀 호출이 빠지지 않았는가

---

## 8. 메시지 처리

- [ ] 모든 수신 경로가 하나의 진입점을 통과하는가
- [ ] 중복 판정이 앱 재시작 후에도 동작하는가 (메모리 집합만 쓰고 있지 않은가)
- [ ] 화면이 도착 순서가 아니라 순번 순서로 읽는가
- [ ] 빠진 항목을 기다리는 코드에 최대 대기 시간이 있는가
- [ ] 순서 판정에 기기 시계를 쓰고 있지 않은가

---

## 9. 휘발성 데이터

- [ ] 입력 중 신호를 타건마다 보내고 있지 않은가
- [ ] 종료 신호가 안 왔을 때 표시가 영원히 남는 경로가 있지 않은가
- [ ] 화면에 보이지 않는 대상까지 구독하고 있지 않은가
- [ ] 온라인 표시를 위해 별도 신호를 보내고 있지 않은가 (하트비트로 대체 가능)
- [ ] 온라인·오프라인·모름 세 상태를 구분하는가

---

## 10. 이벤트와 렌더링

- [ ] 이벤트를 받을 때마다 DB 쓰기나 화면 갱신을 하고 있지 않은가
- [ ] 합치기를 적용한 데이터가 정말 버려도 되는 것인가 (메시지·주문·로그에 쓰고 있지 않은가)
- [ ] 흐름 종료 시 버퍼에 남은 마지막 값을 내보내는가
- [ ] 사용자 직접 행동에 억제를 걸고 있지 않은가
- [ ] 수신 시각과 화면 반영 시각의 차이를 측정하고 있는가

---

## 11. 푸시

- [ ] 푸시로 온 데이터를 그대로 저장하고 있지 않은가 (동기화로 확인하는가)
- [ ] 토큰이 바뀔 때 서버에 갱신하는 처리가 있는가
- [ ] 메시지처럼 독립적인 데이터에 대체 식별자를 쓰고 있지 않은가
- [ ] 앱이 실행될 때 동기화가 항상 실행되는가

---

## 12. 보안과 자원

- [ ] 민감 값에 `toString()`을 호출하고 있지 않은가
- [ ] 지우는 함수가 최적화로 제거될 수 있는 것을 쓰고 있지 않은가
- [ ] 해제 훅에서 0으로 덮은 다음에 메모리를 반환하는가
- [ ] 앱이 백그라운드로 갈 때 민감 값을 정리하는 훅이 있는가
- [ ] 메모리에 평문이 남지 않는지 자동으로 검증하고 있는가
- [ ] 수명이 긴 객체가 수명이 짧은 자원을 참조하고 있지 않은가
- [ ] 프레임마다 반복 생성되는 임시 객체를 하나씩 관리하고 있지 않은가
- [ ] 버퍼를 돌려쓸 때 이전 내용을 지우는가

---

## 리뷰 결과 작성 형식

```markdown
## 리뷰 결과

### 지금 고쳐야 함
1. **[제목]**
   - 위치: [파일/함수]
   - 문제: [무엇이 잘못됐는가]
   - 재현 조건: [언제 나타나는가]
   - 영향: [사용자에게 무엇이 보이는가]
   - 수정: [어떻게]

### 곧 고쳐야 함
[같은 형식. 규모가 얼마가 되면 문제가 되는지 숫자로]

### 지켜볼 것
[판단선과 현재 값을 함께]

### 과한 설계 (제거 후보)
[왜 지금 규모에 과한지, 언제 다시 필요해지는지]
```

**우선순위 판단:** 데이터 유실 > 보안 노출 > 사용자에게 보이는 오동작 > 규모 위험 > 유지보수 비용. 이 순서로 정렬한다.
